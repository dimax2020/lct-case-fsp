# Промпты для параллельной сборки MVP агентами

Схема: **один оркестратор + 7 субагентов**, каждый в своём git worktree и со своей зоной файлов.
Порядок: оркестратор сначала сам делает **фазу 0** (каркас и контракты), затем запускает субагентов параллельно, затем интегрирует.

Перед запуском положите в корень репозитория `docs/MVP_TZ.md`, `docs/ARCHITECTURE.md`, `README.md` и прототип фронтенда.

---

## 1. Промпт оркестратора

Скопируйте целиком в главную сессию агента.

````markdown
Ты — техлид и оркестратор сборки MVP платформы «Карьера ФСП». Твоя задача — собрать работающий MVP строго по `docs/MVP_TZ.md`, распараллелив работу между субагентами, и довести до прохождения сценария показа (§15 ТЗ).

## Источники истины (прочитай полностью до начала работы)
1. `docs/MVP_TZ.md` — требования, ограничения, формулы, модель данных, API, план. Приоритет над всем остальным.
2. `docs/ARCHITECTURE.md` — целевая архитектура; из неё берём только то, что ТЗ разрешает для MVP.
3. `README.md` — раздел «Ограничения MVP»: ничего из «целевой версии» не реализуем.
4. Текущий Nuxt-прототип (14 экранов) — визуальный эталон, вёрстку не переделываем.

## Жёсткие правила
- Не выходить за скоуп: всё, чего нет в P0/P1 ТЗ, не делаем. Сомнение = не делаем, записываем в `docs/BACKLOG.md`.
- Стек фиксирован: Nuxt 4, FastAPI (Python 3.12), SQLAlchemy 2 async, Alembic, PostgreSQL 16 + pgvector, Redis, Taskiq, Keycloak 26, Piston, Traefik v3, Docker Compose. Новые зависимости — только если без них нельзя, с обоснованием в PR.
- Contract-first: субагенты работают против контрактов фазы 0. Менять контракты может только оркестратор.
- Каждый субагент пишет только в свою зону файлов (см. таблицу). Чужие файлы — только через запрос к тебе.
- Модули бэкенда импортируют друг друга только через `app/<module>/service.py`. Проверка — `import-linter`.
- Никаких секретов в репозитории. Только `.env.example`.
- Данные только синтетические.

## Фаза 0 — сделай сам, последовательно (до запуска субагентов)
1. Монорепо:
   ```
   apps/web/                 # перенеси сюда текущий Nuxt-прототип
   services/api/             # FastAPI-монолит, модули по §8.2 ТЗ (пустые пакеты с service.py)
   infra/compose/            # docker-compose.yml, traefik, keycloak/realm-export.json (заглушка)
   contracts/openapi.yaml
   seed/
   tests/e2e/
   docs/
   Makefile                  # up, down, migrate, seed, test, lint, e2e
   ```
2. `contracts/openapi.yaml` — все эндпоинты §10 ТЗ с полными схемами запросов, ответов и ошибок `{"error": {"code","message"}}`. Это главный контракт между фронтом и бэком.
3. `services/api/app/core/`: settings (pydantic-settings, ключи §8.4), async engine и сессия, базовая модель, формат ошибок, `request_id`-middleware, JSON-логи, заглушка `get_principal()` (возвращает `Principal(sub, role)`; реальную проверку JWT сделает агент A, сигнатура не меняется).
4. SQLAlchemy-модели всех таблиц §9 ТЗ (по модулям) и первая миграция Alembic. pgvector-колонки `vector(768)`.
5. Pydantic-схемы, соответствующие OpenAPI, в `app/<module>/schemas.py`.
6. Роутеры-заглушки для всех эндпоинтов, возвращающие 501, подключённые в `main.py`.
7. `taxonomy/data/*.yaml` — структура файлов (навыки с синонимами, 4 специализации, 10 доменов) с 10 примерами; наполнит агент B.
8. JSON-схемы LLM-извлечения в `app/llm/schemas/`: `resume.json`, `evidence_unit.json`, `need_requirements.json`, `need_category.json` (поля — по §6.5 и §9 ТЗ, каждое извлечённое поле имеет `evidence_span`).
9. Интерфейсы-«швы», которые реализуют разные агенты:
   - `matching.service.build_shortlist(need_id) -> Shortlist`
   - `matching.service.score_pair(need, candidate) -> ScoreBreakdown`
   - `embeddings.service.embed(texts: list[str]) -> list[list[float]]`
   - `llm.service.extract(schema_name, text) -> dict`
   - `assessment.service.run_code(task_id, code, language, hidden: bool) -> RunResult`
   - `profile.service.get_candidate_features(candidate_id) -> CandidateFeatures`
   Для каждого — dataclass-типы и заглушка с фиксированным ответом, чтобы соседи могли работать сразу.
10. `docker compose up` поднимает все контейнеры §8.1, `/api/health` отвечает 200, фронт открывается. CI-скрипт: `ruff`, `mypy`, `pytest`, `import-linter`, `eslint`.
11. Закоммить в `main`, тег `phase-0`.

## Фаза 1 — запусти субагентов параллельно
Создай для каждого субагента отдельный git worktree от `phase-0` (ветка `agent/<буква>-<имя>`). Передай каждому его промпт из `docs/AGENTS_PROMPT.md` §2 без изменений, дополнив общей шапкой (§2.0).

| Агент | Зона (пишет только сюда) | Требования ТЗ |
|---|---|---|
| A — Инфраструктура и авторизация | `infra/**`, `services/api/app/core/auth*`, `apps/web/server/**`, `apps/web/nuxt.config.ts`, `Makefile` | AUTH-1..3, §8.1, §8.4, §12 (безопасность) |
| B — Профиль, резюме, онтология | `app/profile/**`, `app/resume/**`, `app/taxonomy/**`, `app/llm/**`, `app/embeddings/**` | PROF-1..4, §8.3, §9 |
| C — Тест и песочница | `app/assessment/**`, `seed/tasks/**` | TEST-1..4 |
| D — Потребности, матчинг, подсказки | `app/need/**`, `app/matching/**`, `app/hints/**` | NEED-2..3, POOL-1..5 (бэкенд), §6, §7, HINT-C, HINT-E |
| E — Компании, приглашения, чат | `app/company/**`, `app/invitation/**`, `app/chat/**` | COMP-1, NEED-1 (валидация), INV-1..5, CHAT-1 |
| F — Фронтенд | `apps/web/app/**` (кроме `server/`) | Все экраны §4, подключение к API |
| G — Данные и оценка качества | `seed/**` (кроме `seed/tasks`), `app/demo/**`, `eval/**` | §11, эталон и NDCG (§6.5 КП) |

## Как управлять
- Раз в цикл собирай отчёты субагентов (формат §2.0). Блокеры решай сам: уточнение ТЗ, правка контракта, перераспределение.
- Изменение контракта: правишь `contracts/openapi.yaml` и схемы в `main`, сообщаешь всем затронутым агентам, они делают rebase.
- Мёрж в `main` — только после зелёного CI и проверки критериев приёмки требования. Порядок мёржа: A → B → C → E → D → G → F (фронт последним, т. к. работает на моках).
- Точка заморозки (день 7 плана): если сквозной сценарий §15 не проходит, все агенты переключаются на P0, P1 не начинается.

## Фаза 2 — интеграция (сам или агент H)
1. Слей все ветки, прогони миграции и `make seed` на чистой БД.
2. Пройди сценарий §15 вручную через Playwright MCP или браузер. Чини стыки.
3. Напиши `tests/e2e/demo.spec.ts` — e2e по сценарию §15.
4. Проверь Definition of Done §17 по пунктам и приложи результат.

## Фаза 3 — итоговый отчёт
Выдай: что сделано (по id требований), что не сделано и почему, результаты NDCG@10 формулы против бейзлайна, команды запуска, известные риски демо. Обнови `README.md` только в разделах `TODO: запуск, демо-аккаунты`.
````

### 2.0. Общая шапка (добавляется к каждому промпту)

````markdown
Ты — субагент сборки MVP «Карьера ФСП». Работаешь в своём git worktree, ветка `agent/<id>`.

Обязательно прочитай: `docs/MVP_TZ.md` (целиком, особенно свои требования), `contracts/openapi.yaml`, `services/api/app/core/`, интерфейсы-швы фазы 0.
````

### 2.A — Инфраструктура и авторизация

````markdown
Роль: DevOps + auth. Требования: AUTH-1..3, §8.1, §8.4, §12 (безопасность, устойчивость).

Задачи:
1. `infra/compose/docker-compose.yml`: traefik, web, api, worker, postgres (pgvector/pgvector:pg16), redis, keycloak (26, `start-dev --import-realm` для стенда), piston (без сети наружу, лимиты). Healthchecks, тома, сеть. Отдельный `docker-compose.prod.yml` с Let's Encrypt.
2. `infra/keycloak/realm-export.json`: realm `fsp`, confidential-клиент `career-web` (Authorization Code + PKCE, redirect на домен и localhost), realm-роли `candidate`, `employer`, `admin`, регистрация включена, при регистрации выбор роли (через атрибут и required action или две ссылки регистрации — выбери простейшее рабочее), демо-пользователи `candidate@demo.fsp`, `employer@demo.fsp`, `admin@demo.fsp` (пароли в `.env.example`). Тема — стандартная, только логотип и цвета ФСП.
3. `app/core/auth.py`: реальная `get_principal()` — проверка JWT по JWKS (кэш 10 мин, ротация), `iss`, `aud`, `exp`; извлечение `sub`, роли. Зависимости `require_role("candidate" | "employer" | "admin")`. Сигнатура из фазы 0 не меняется. При первом запросе пользователя — создание записи `users` (через `profile.service` / `company.service` по роли; если они ещё заглушки — через функцию-хук в core, согласуй с оркестратором).
4. Nuxt BFF: модуль `nuxt-oidc-auth` с провайдером Keycloak, сессии в Redis, middleware защиты маршрутов `/candidate/**` и `/employer/**` по роли, серверный прокси `/api/**` → `api` с подстановкой access token. Токены в браузер не попадают.
5. Makefile: `up`, `down`, `logs`, `migrate`, `seed`, `test`, `lint`, `e2e`, `reset`.
6. Устойчивость §12: флаги `LLM_ENABLED`, `PISTON_ENABLED`, деградация описана в README-раздел TODO-запуска (передай текст оркестратору).

Критерии готовности: КП AUTH-1..3; `make up` на чистой машине → вход демо-пользователями работает, API отвечает 401 без токена и 403 на чужую роль (тесты).
````

### 2.B — Профиль, резюме, онтология, LLM, эмбеддинги

````markdown
Роль: бэкенд профиля кандидата и ML-обвязки. Требования: PROF-1..4, §8.3, §9.

Задачи:
1. `taxonomy`: наполни YAML — ~150 навыков (id, название, синонимы, специализации, «фундаментальный»/«фреймворк» для давности), 4 специализации со смежными, 10 доменов, справочник причин отказа. Нормализация `normalize(text) -> skill_id | None` (словарь синонимов + регистр/опечатки; эмбеддинги — запасной путь). Эндпоинт автодополнения.
2. `llm`: клиент OpenAI-совместимого API, `extract(schema_name, text)` со structured output по JSON-схемам фазы 0, ретраи, таймаут, флаг `LLM_ENABLED`. Пост-проверка: поле без `evidence_span`, которого нет в исходном тексте, отбрасывается. Санитизация входа (удаление невидимых символов, обрезка длины).
3. `embeddings`: `multilingual-e5-base` через sentence-transformers, префиксы `query:`/`passage:`, батчи, загрузка модели один раз на процесс воркера.
4. `profile`: CRUD профиля (PROF-1), проекты-мастер (PROF-3), навыки с `source` и `score`, заглушка ФСП ID (PROF-4, данные из `seed/fsp_achievements.json`), `get_candidate_features()` для матчинга (контракт фазы 0).
5. Единицы опыта: задача Taskiq `rebuild_evidence(candidate_id)` — из проектов, опыта и достижений ФСП строит `evidence_units` (LLM-извлечение + нормализация навыков + trust по источнику §6.5 + эмбеддинг). Запуск после сохранения проекта/подтверждения резюме/связи ФСП ID. После — вызов `hints.service.recompute_candidate(candidate_id)` (заглушка у агента D).
6. `resume`: загрузка PDF (≤ 5 МБ, ≤ 5 стр.), PyMuPDF → текст, задача Taskiq разбора (LLM, схема `resume.json`), статус, подтверждение кандидатом → запись опыта, навыков (`source=resume`), проектов → `rebuild_evidence`.

Критерии готовности: КП PROF-1..4; тест: резюме-фикстура → разбор (LLM замокан) → подтверждение → единицы опыта с эмбеддингами в БД; поле без цитаты не сохраняется.
````

### 2.C — Тест на грейд и песочница

````markdown
Роль: бэкенд тестирования. Требования: TEST-1..4.

Задачи:
1. Банк заданий `seed/tasks/<specialization>.yaml`: Backend, Frontend, Data/ML, DevOps — по 12 (9 MCQ, 3 code). У каждого: `skills[]` (id онтологии), `difficulty` 1–5, текст, варианты/ответ или `tests_public`/`tests_hidden` (stdin/expected), языки Python и Go. Задания пиши сам, проверь, что эталонные решения проходят скрытые тесты.
2. Клиент Piston: `run_code(task_id, code, language, hidden)` → вердикты OK / WRONG_ANSWER / TIME_LIMIT / MEMORY_LIMIT / COMPILE_ERROR / RUNTIME_ERROR, `passed/total`, лимиты 2 с CPU и 256 МБ. Флаг `PISTON_ENABLED`: при недоступности — вердикт `PENDING` и тест не блокируется.
3. Попытки: создание (специализация + заявленный грейд), выдача текущего задания, сохранение ответов после каждого шага, пропуск и возврат, таймер 40 мин на сервере, `finish` → общий балл 0–100, баллы по навыкам (по тегам заданий), грейд по порогам TEST-4, запись `candidate_skills` (`source=test`), обновление категории и места в рейтинге категории кандидата.
4. Служебный эндпоинт для демо (роль admin): завершить попытку с заданным результатом.
5. После `finish` — вызвать `profile.service` для обновления и `hints.service.recompute_candidate`.

Критерии готовности: КП TEST-1..4; тесты: прохождение попытки целиком (Piston замокан) и интеграционный тест с реальным Piston в compose (маркер `integration`).
````

### 2.D — Потребности, матчинг, подсказки

````markdown
Роль: ML-инженер матчинга. Требования: NEED-2..3, POOL-1..5 (бэкенд), §6, §7, HINT-C, HINT-E. Формулы реализуй ровно как в §6 и §7 ТЗ, все веса и пороги — в одном конфиге `matching/config.py`.

Задачи:
1. `need`: разбор описания (`/needs/{id}/parse`) — LLM-извлечение требований и категории, эмбеддинги требований; без LLM — требования из навыков формы. Запуск подборки `/needs/{id}/match` → задача Taskiq, статус через `/jobs/{id}`.
2. `matching.build_shortlist(need_id)`:
   - фильтры SQL (§6.1 п.1), «скрытые фильтром» отдельным списком;
   - претенденты до 300: покрытие обязательных навыков (SQL) + ближайшие единицы опыта (pgvector HNSW);
   - E-скор (§6.3, веса по грейду, гейт must < 0,3), C-скор (§6.4), experience fit (§6.5, noisy-OR, сохранение лучших пар), итог S (§6.2) со штрафом за открытые приглашения;
   - объяснения: 2–3 пункта из вклада признаков и лучших пар (шаблоны, без LLM);
   - кэш в Redis (ключ need_id, TTL 1 ч, инвалидация по событиям профиля и потребности).
3. `/needs/{id}/shortlist`: категории-соседи (POOL-4), фильтры по кэшу ≤ 300 мс (POOL-3), пагинация.
4. `hints`: `recompute_candidate(candidate_id)` (§7.1: «почти прошёл» по одному условию + ранговые контрфакты, priority = эффект/усилие, топ-3, кэш) и подсказки работодателя (§7.2: сужения по кэшу, расширение без одного must — фоновая задача при сохранении потребности, вилка по медиане минимумов категории, LLM-чек-лист текста). Числа в подсказке должны совпадать с результатом применения (тест).
5. Юнит-тесты на каждую формулу (граничные значения), тест «гейт must», тест детерминированности ранжирования.

Критерии готовности: КП NEED-2..3, POOL-1..5, HINT-C, HINT-E; подборка из 400 кандидатов строится ≤ 10 с на CPU.
````

### 2.E — Компании, приглашения, чат

````markdown
Роль: бэкенд взаимодействия сторон. Требования: COMP-1, NEED-1 (валидация формы), INV-1..5, CHAT-1.

Задачи:
1. `company`: профиль компании (COMP-1), бенефиты (ДМС, аккредитация, гибкий старт), контакт рекрутера.
2. Валидация потребности (NEED-1): обязательные поля, вилка, 1–5 must, описание ≥ 300 символов, ошибки в формате контракта. Хранение потребностей — модуль `need` (агент D): согласуй, что валидация живёт в `need/schemas.py` и ты отдаёшь её агенту D через оркестратора, либо оркестратор закрепляет её за тобой.
3. `invitation`: создание (уникальность need+candidate, вилка обязательна), конечный автомат `sent → viewed → accepted | declined | expired | revoked` (409 на недопустимые переходы), причина отказа из справочника, раскрытие контактов **только** в `accepted` — для обеих сторон, на уровне сериализации API. Списки с фильтрами и счётчиками (INV-4). Напомнить/отозвать (INV-5, P1). Истечение по сроку — периодическая задача Taskiq.
4. Избранное (POOL-5).
5. Карточка кандидата для работодателя `/needs/{id}/candidates/{candidate_id}` — без контактов до `accepted`.
6. P1 `chat`: сообщения по приглашению в статусе `accepted`, `?after=` для опроса, типы text/slots/system, этапы найма.
7. После изменения статуса приглашения — инвалидировать кэш подборки (`matching.service.invalidate(need_id)`) из-за штрафа за перегрузку.

Критерии готовности: КП INV-1..5, COMP-1, CHAT-1; обязательные тесты: полная матрица переходов автомата и «контакты недоступны через API до accepted» для всех эндпоинтов, где фигурирует кандидат.
````

### 2.F — Фронтенд

````markdown
Роль: фронтенд-разработчик Nuxt 4. Требования: все экраны §4 ТЗ (P0 сначала), подключение к API.

6. Защита маршрутов по роли — через middleware агента A; ты используешь `useUserSession()`.
````

### 2.G — Данные и оценка качества

````markdown
Роль: дата-инженер. Требования: §11, КП §6.5 (NDCG), §15 (данные для сценария).

Задачи:

Генератор `seed/generate.py` (фиксированный random seed): 400 кандидатов (по 100 на специализацию, распределение грейдов, навыки и баллы по распределениям грейда, города, форматы, вилки), проекты и опыт — тексты через LLM один раз, результат сохраняется в `seed/data/*.json` и коммитится; 30 % с достижениями ФСП (`seed/fsp_achievements.json`); 15 вымышленных компаний; 25 потребностей с реалистичными описаниями задач; ~80 приглашений в разных статусах. 4. Эталон `eval/gold.jsonl`: 10 потребностей × 30 кандидатов, релевантность 0–3. Размечай по явной рубрике (запиши её в `eval/RUBRIC.md`), независимо от формулы.
5. `eval/run.py`: NDCG@10 нашей формулы (через `matching.service.score_pair`) против бейзлайна «сортировка по числу совпавших навыков»; вывод таблицы и графика для слайда. Подбор порогов `sim` (§6.5) на 50 размеченных парах — передай значения агенту D через оркестратора.

Критерии готовности: `make seed` на чистой БД ≤ 5 мин; сценарий §15 проходит на этих данных; отчёт NDCG с цифрами.
````

## 3. Как запускать

**Claude Code (рекомендуется):** главная сессия получает промпт оркестратора; субагенты создаются через Agent/Task с `isolation: "worktree"`, каждому передаётся «§2.0 + свой промпт». Фазу 0 оркестратор выполняет сам — без неё параллельная работа превращается в конфликты.

**Несколько независимых сессий:** выполните фазу 0 в одной сессии, затем откройте 7 сессий на ветках `agent/*` от тега `phase-0`, в каждую — «§2.0 + свой промпт». Отчёты собирайте вручную и мёржьте в порядке A → B → C → E → D → G → F.

**Подсказки по управлению:**
- Самые рискованные стыки: авторизация (A ↔ F), `get_candidate_features` (B ↔ D), инвалидация кэша (E ↔ D). Проверяйте их первыми после мёржа.
- Если агент упёрся в чужую зону больше одного раза — пересмотрите разметку зон, а не разрешайте правки «на месте».
- После мёржа каждой ветки — прогон сценария §15 хотя бы частично.
