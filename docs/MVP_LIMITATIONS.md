# Ограничения MVP: что сейчас, что будет и почему

Это демонстрационная версия, собранная к защите кейса. Мы сознательно упростили инфраструктуру и ML, но **не упрощали предметную логику**: сквозной сценарий (резюме → тест → категория → подборка → приглашение → контакты) работает на живых данных, а каждое упрощение заменяется без переписывания остальной системы.

Полная целевая архитектура — [docs/ARCHITECTURE.md](ARCHITECTURE.md), ТЗ на MVP — [docs/MVP_TZ.md](MVP_TZ.md).

### Главный принцип

> **Упрощаем «как устроено», не упрощаем «что делает».**
> Границы модулей в MVP совпадают с будущими микросервисами, формулы матчинга — с признаками будущих ML-моделей, а все внешние зависимости (LLM, песочница, авторизация) подключены через стандартные интерфейсы. Замена реализации не затрагивает соседей.

### Архитектура и инфраструктура

| Область | В MVP сейчас | В целевой версии | Почему так сейчас |
|---|---|---|---|
| Бэкенд | Модульный монолит на FastAPI + один фоновый воркер (Taskiq) | Микросервисы на FastAPI | При одной команде и 10 днях микросервисы добавляют сетевые вызовы, отдельные деплои и распределённые ошибки, не добавляя функций. Модули разделены как сервисы, импорт между ними — только через публичный интерфейс (проверяется линтером), поэтому их можно вынести по одному |
| Шина событий | Вызовы между модулями внутри процесса, фоновые задачи через Redis | Kafka + transactional outbox | Kafka нужна, когда событиями пользуются много потребителей (аналитика, ML, уведомления). В демо потребитель один |
| Хранилища | PostgreSQL + pgvector, Redis | Отдельные БД на сервис, Qdrant, ClickHouse, MinIO, OpenSearch | На демо-объёме (сотни профилей) PostgreSQL с pgvector закрывает поиск, векторы и аналитику. Схемы разделены по модулям |
| Развёртывание | Docker Compose + Traefik на одном сервере | Kubernetes, Helm, ArgoCD, автомасштабирование | Одного сервера хватает для показа; Compose поднимает стенд одной командой |
| Наблюдаемость | Структурированные логи, `request_id` | OpenTelemetry, Prometheus, Grafana, Loki, Sentry | Для демо достаточно логов; трассировка нужна при распределённой системе |

### Матчинг и ML

| Область | В MVP сейчас | В целевой версии | Почему так сейчас |
|---|---|---|---|
| Ранжирование | Экспертная линейная формула с весами по грейдам: «подходит ли кандидат работодателю» × «подходит ли предложение кандидату» × штраф за перегрузку | Две обученные модели LambdaMART: вероятность приглашения и вероятность принятия | Модели учатся на реальных приглашениях и откликах, а их ещё нет. Формула использует те же признаки и становится запасным режимом и базовой линией для сравнения |
| Experience fit (опыт ↔ задачи команды) | Разбор текста LLM на единицы опыта и требования, сравнение эмбеддингами, поправки на подтверждённость, давность и роль | То же + cross-encoder и LLM-судья для точной оценки пар | Эмбеддинги дают достаточную точность на демо-объёме; точные модели добавляются как отдельный шаг без изменения формулы |
| Качество | Ручной эталон (10 потребностей × 30 кандидатов), метрика NDCG@10 против сортировки по навыкам | Онлайн-метрики: доля взаимного принятия, A/B-тесты | Это единственный честный способ доказать качество до появления реальных пользователей |
| Подсказки | Расчёт «почти прошёл» и пересчёт скора с изменённым условием | То же + обучение типов подсказок по реальным результатам (бандиты) | Механика та же; обучение требует истории показов и действий |
| LLM | OpenAI-совместимый API, адрес задаётся в настройках | Собственные модели в контуре (vLLM) | Нет GPU на демо-стенде. В MVP используются только синтетические данные, поэтому внешний провайдер допустим. Переключение — смена `LLM_BASE_URL` |
| Эмбеддинги | `multilingual-e5-base` на CPU | `bge-m3` и reranker на GPU через TEI | Для сотен профилей CPU достаточно; векторы считаются один раз |
| Онтология навыков | Статический справочник (~150 навыков, синонимы), 4 специализации | Сервис онтологии с графом навыков, ~20–25 ролей, пополнение из текстов | Четырёх специализаций хватает, чтобы показать механику; справочник загружается тем же интерфейсом |
| Категоризация вакансий | LLM со схемой таксономии + подтверждение работодателем | Дообученный классификатор, LLM только для неясных случаев | Классификатору нужна размеченная выборка |

### Тестирование и выполнение кода

| Область | В MVP сейчас | В целевой версии | Почему так сейчас |
|---|---|---|---|
| Тест на грейд | Адаптивный тест (CAT, IRT 2PL) на банке из 288 параметризованных шаблонов; параметры a и b — стартовые, проверены симуляцией (`tmp_bank/sim.py`) | Калибровка a, b и порогов грейдов на реальных прохождениях, онлайн-контроль дрейфа | Калибровке нужны сотни реальных прохождений; до них параметры задаёт эксперт и подтверждает симуляция |
| Песочница | Piston (open-source), без сети, лимиты CPU, памяти и времени; Python и Go | Собственный runner на gVisor/Firecracker, пул прогретых песочниц, 6+ языков | Готовое решение даёт изоляцию и вердикты за один день вместо недели |
| Честность теста | Скрытые тесты | + уникальные варианты задач под кандидата, антиплагиат | Требует генератора вариантов и истории решений |

### Профиль, резюме, интеграции

| Область | В MVP сейчас | В целевой версии | Почему так сейчас |
|---|---|---|---|
| Парсинг резюме | Только PDF с текстовым слоем, до 5 страниц; каждое поле с цитатой-источником; подтверждение кандидатом | + OCR сканов, DOCX, разметка блоков | Основной поток резюме — текстовые PDF; OCR добавляется как отдельный шаг конвейера |
| Авторизация | Keycloak: один realm, вход по почте, роли «кандидат» и «работодатель» | + организации для компаний, MFA, вход через ФСП ID, Яндекс ID, VK ID | Интеграция с Keycloak по ТЗ заложена сразу: сервисы проверяют стандартный OIDC-токен, поэтому расширение — это настройка Keycloak, а не изменение кода |
| ФСП ID | Заглушка: кнопка подтягивает достижения из тестовых данных | Реальная связь с ФСП ID и официальными условиями кейсов хакатонов | Нужен доступ к API ФСП |
| Уведомления | Счётчики в интерфейсе | Почта, push, Telegram, дайджесты | Не влияет на демонстрацию матчинга |
| Чат | Обновление раз в 5 секунд | WebSocket | Для демо разница незаметна |

### Данные и правовые вопросы

| Область | В MVP сейчас | В целевой версии | Почему так сейчас |
|---|---|---|---|
| Данные | Только синтетические: вымышленные кандидаты и компании | Реальные пользователи | Демо не обрабатывает персональные данные |
| 152-ФЗ | Решение о приглашении принимает человек, контакты раскрываются только после согласия кандидата (проверяется на сервере). Согласия хранятся с датой, настройки приватности (имя, место работы, ФСП, PDF, тест рабочего стиля, скрытые компании) применяются в подборке, банке, карточке и приглашениях; тексты согласий — `/legal/privacy`, `/legal/terms` | Раздельные юридически значимые согласия, журнал доступа к ПДн, шифрование полей, процедура возражения против автоматизированной обработки, хранение в РФ | Юридическая часть вводится вместе с реальными данными; логика «человек принимает решение» и раскрытие контактов заложены уже сейчас |
| Справедливость | Пол, возраст, фото и имя не используются в скоринге | + регулярный аудит долей приглашений по группам | Аудит требует реальной статистики |

### Интерфейс

- Адаптивная вёрстка (точки перелома 960 и 640 px) и светлая/тёмная тема с переключателем в шапке.
- Публичный каталог вакансий и откликов есть как дополнительный сценарий: продукт строится вокруг обратного подбора.

### Тест рабочего стиля

Необязательный тест для кандидата (`/candidate/psych`, около 20 минут): часть 1 — 12 блоков DISC с отметками «+» и «−», часть 2 — 30 утверждений по шкале 1–5, часть 3 — 5 рабочих ситуаций. Подсчёт — на сервере по ключу методики (`services/api/app/psych`), ключ клиенту не передаётся. Кандидат видит свой стиль, уровни четырёх шкал и индексы соответствия; работодатель — дополнительно сырые баллы, социальную желательность и флаги надёжности, и только если кандидат открыл доступ. Результат на категорию и ранжирование не влияет. Подробнее — [docs/PSYCH_TEST.md](PSYCH_TEST.md).

### Что заменяется первым после показа

1. Тест и песочницу, парсинг резюме — в отдельные сервисы с очередями (им нужно своё масштабирование).
2. Kafka и ClickHouse — начинаем собирать метки: показы, приглашения, принятия.
3. Обучение моделей ранжирования на собранных метках; линейная формула остаётся запасной.
4. Собственная песочница на gVisor и адаптивный тест.
5. Реальный ФСП ID, организации и MFA в Keycloak.
