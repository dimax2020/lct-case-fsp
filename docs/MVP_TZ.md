# ТЗ на MVP «Карьера ФСП»

> Документ для команды: что именно строим для показа заказчику, в каких границах и в каком порядке.
> Целевая архитектура описана в [ARCHITECTURE.md](./ARCHITECTURE.md). MVP — её урезанная версия: модули совпадают с будущими сервисами, поэтому после показа систему можно развивать, а не переписывать.

---

## 0. Допущения

| Параметр | Значение |
|---|---|
| Срок | **10 рабочих дней** до показа |
| Команда | 4 человека: фронтенд, бэкенд ×2, ML и данные |
| Данные | Только синтетические (сгенерированные). Реальных персональных данных нет |
| Среда показа | Один VPS (8 vCPU, 16 ГБ RAM, без GPU), домен + HTTPS |
| Фронтенд | Готовый прототип на Nuxt 4 (`apps/web`, 14 экранов) — подключаем к API, а не верстаем заново |

Если срок или состав другие, режется раздел P1 (см. §4), а P0 не трогается.

## 1. Цель MVP

Показать заказчику **сквозной сценарий обратного матчинга** на живых данных:

1. Кандидат регистрируется, загружает резюме, проходит тест с выполнением кода и получает категорию и место в рейтинге.
2. Работодатель описывает потребность свободным текстом и за секунды получает ранжированную подборку с объяснениями «почему в подборке».
3. Обе стороны видят подсказки, которые меняют выдачу.
4. Работодатель отправляет приглашение с вилкой, кандидат принимает, контакты открываются.

**Критерий успеха показа:** сценарий из §15 проходит от начала до конца без ручных вмешательств за 7 минут.

| 14 | **Без уведомлений по почте, push и Telegram:** только счётчики в интерфейсе | notification-сервис |
| 15 | **Чат — REST + опрос раз в 5 с**, без WebSocket | Centrifugo |
| 16 | **Развёртывание — Docker Compose + Traefik** на одном сервере | K8s, ArgoCD |

## 5. Функциональные требования

Каждое требование имеет id и критерии приёмки (КП). Требование считается выполненным, когда выполнены все КП.

### 5.1. Авторизация (P0)

**AUTH-1. Вход через Keycloak.**
- КП: незалогиненный пользователь на любом кабинетном маршруте перенаправляется в Keycloak и после входа возвращается на исходный маршрут.
- КП: токены хранятся только на сервере Nuxt (BFF), в браузере — httpOnly-cookie.
- КП: API отклоняет запрос без валидного JWT (401) и с чужой ролью (403).

**AUTH-2. Регистрация с ролью.**
- КП: при регистрации выбирается роль; пользователь получает realm-роль `candidate` или `employer`.
- КП: при первом входе создаётся запись профиля или компании, связанная по `sub`.

**AUTH-3. Демо-пользователи.** `candidate@demo.fsp` / `employer@demo.fsp` с заранее заполненными данными.

### 5.2. Профиль кандидата и резюме (P0)

**PROF-1. Условия поиска:** специализация, минимальная зарплата, формат (удалённо, гибрид, офис), город, статус поиска, интересные и нежелательные технологии и домены.
- КП: без минимальной зарплаты и формата профиль не участвует в подборках, а в интерфейсе висит подсказка.

**PROF-2. Загрузка резюме PDF.**
- КП: файл до 5 МБ и 5 страниц; иначе понятная ошибка.
- КП: в течение 30 секунд появляется форма подтверждения с извлечёнными полями: опыт (компания, роль, период, описание), навыки, проекты.
- КП: у каждого поля есть цитата-источник из резюме (подсказка при наведении); поле без цитаты не сохраняется.
- КП: кандидат может исправить и подтвердить; навыки из резюме получают `source = resume`.

**PROF-3. Проекты и хакатоны — мастер, а не свободный текст.** Поля: задача, роль (сделал сам / в команде / участник), технологии (из онтологии с автодополнением), масштаб (необязательно), результат, дата, ссылка.
- КП: после сохранения за 10 секунд из проекта строятся единицы опыта с эмбеддингами.

**PROF-4. ФСП ID (заглушка).** Кнопка «Связать ФСП ID» подтягивает из сида 0–3 достижения с дисциплиной и местом. `source = fsp_id`.

### 5.3. Тест на грейд (P0)

> Реализован адаптивный вариант: механика, банк, правила грейда и интерфейс описаны в [`GRADE_TEST.md`](GRADE_TEST.md). Требования ниже — исходный фиксированный тест, он остался запасным режимом.

**TEST-1. Опрос:** специализация и предполагаемый грейд → набор заданий.

**TEST-2. Задания.** На каждую из 4 специализаций по 12 заданий: 9 с выбором ответа, 3 с кодом. Время — 40 минут.
- КП: таймер, прогресс, пропуск, возврат к пропущенным.
- КП: ответы сохраняются на сервере после каждого задания; перезагрузка страницы не теряет прогресс.

**TEST-3. Задания с кодом.**
- КП: кандидат пишет решение в редакторе (Monaco, языки Python и Go), кнопка «Запустить» прогоняет открытые примеры, «Отправить» — скрытые тесты.
- КП: результат за ≤ 5 секунд: вердикт (OK, неверный ответ, превышено время или память, ошибка компиляции), сколько тестов прошло.
- КП: код выполняется без сети, с лимитами 2 с CPU и 256 МБ памяти.

**TEST-4. Итог.**
- КП: общий балл 0–100 и баллы по навыкам (теги заданий).
- КП: грейд по порогам: < 40 — на ступень ниже заявленного, 40–74 — заявленный, ≥ 75 — заявленный с пометкой «готов к следующему».
- КП: категория (специализация + грейд) и место в рейтинге категории видны в профиле.
- КП: навыки из теста получают `source = test` и балл.

### 5.4. Компания и потребность (P0)

**NEED-1. Форма потребности.** Обязательные поля:
- название роли, специализация, грейд (можно два соседних);
- вилка «от — до» в рублях (без вилки сохранить нельзя);
- формат и город;
- 1–5 обязательных навыков и до 5 желательных (из онтологии);
- описание задач команды — не меньше 300 символов, с подсказкой «что человек будет делать первые 3 месяца»;
- домен продукта;
- число этапов найма.

КП: при попытке указать больше 5 обязательных навыков форма предлагает перенести лишние в желательные.

**NEED-2. Разбор описания.** При сохранении LLM раскладывает описание на требования (задача, домен, навыки, масштаб, обязательное или желательное) и предлагает категорию.
- КП: разобранные требования показаны работодателю списком; их можно удалить или переключить «обязательно / желательно».
- КП: если LLM недоступна, потребность сохраняется, а матчинг работает по навыкам из формы без experience fit.

**NEED-3. Запуск подборки.** Кнопка «Сформировать подборку» → подборка готова ≤ 10 с (фоновая задача, индикатор прогресса).

**COMP-1 (P1).** Профиль компании: название, город, размер, направление, описание, контакт рекрутера.

### 5.5. Подборка (P0)

**POOL-1. Ранжированный список** по скору из §6 с номером позиции.
- КП: в карточке — имя в формате «Имя Ф.», категория, опыт, город, бейдж ФСП, полоса соответствия (цвет по порогам ≥ 80 / 50–79 / < 50), 2–3 пункта «почему в подборке», статус приглашения, если оно уже отправлено.
- КП: контакты в подборке не показываются никогда.

**POOL-2. Объяснения** строятся из вклада признаков и лучших пар «требование ↔ доказательство», без генерации LLM на лету.
- КП: каждый пункт ссылается на проверяемый факт: балл теста, достижение, проект.

**POOL-3. Фильтры** в боковой панели: только с ФСП, дисциплина ФСП, минимальный балл теста, стек (поиск), формат, «активен за 30 дней».
- КП: применение фильтра ≤ 300 мс, без повторного расчёта подборки (фильтрация кэшированного списка).
- КП: строка «Уточнения» показывает активные фильтры, каждый снимается кликом; исходная подборка сохраняется.

**POOL-4. Категории-соседи.** Над списком — до 3 плиток категорий (основная и смежные) с числом кандидатов; клик переключает список.

**POOL-5. Избранное.** Добавить или убрать кандидата; вкладка «Избранные».

### 5.6. Приглашения (P0)

**INV-1. Отправка.** Из профиля кандидата: должность, текст предложения, вилка (из потребности, можно изменить), способ связи, срок ответа.
- КП: вилка обязательна.
- КП: нельзя отправить повторное приглашение тому же кандидату по той же потребности.

**INV-2. Конечный автомат:** `sent → viewed → accepted | declined | expired | revoked`.
- КП: недопустимые переходы возвращают 409.
- КП: `viewed` ставится при первом открытии кандидатом.
- КП: `declined` требует причину из справочника (не подходит вилка, стек, формат, уже нашёл работу, другое).

**INV-3. Раскрытие контактов.** Почта и телефон кандидата видны работодателю **только** в статусе `accepted`; контакт рекрутера виден кандидату тоже только после `accepted`.
- КП: покрыто unit-тестом на уровне API (не только интерфейса).

**INV-4. Списки.** У кандидата — вкладки «Входящие, Принятые, Отклонённые»; у работодателя — «Все, Ждут ответа, Принятые» и счётчики по статусам.

**INV-5 (P1).** «Напомнить» и «Отозвать» для приглашений без ответа.

### 5.7. Подсказки (P0)

**HINT-C. Кандидату — топ-3** в профиле, по алгоритму §7.1.
- КП: каждая подсказка содержит действие, числовой эффект и кнопку, ведущую к действию (тест, форма проекта, настройки).
- КП: после выполнения действия подсказки пересчитываются ≤ 30 с.

**HINT-E. Работодателю — топ-3** над подборкой, по алгоритму §7.2.
- КП: «Применить» меняет список мгновенно и добавляет уточнение, которое можно снять.
- КП: числа в подсказке («24 → 9») совпадают с фактическим результатом после применения.

### 5.8. Чат (P1)

**CHAT-1.** Диалог открывается после `accepted`. Сообщения, опрос новых раз в 5 с, предложение слотов интервью, отметка этапа найма (интервью, команда, оффер, закрыт).

## 6. Матчинг в MVP

### 6.1. Конвейер

1. **Фильтры (SQL):** специализация (основная или смежная), грейд ±1, `need.salary_to ≥ candidate.min_salary × 0,9`, формат совместим, статус «ищу / открыт», профиль виден, домен не в «не рассматриваю».
2. **Кандидаты-претенденты:** до 300 по сумме покрытия обязательных навыков (SQL) и близости эмбеддингов единиц опыта к требованиям (pgvector, HNSW).
3. **Скоринг в Python** по формулам ниже.
4. **Кэш** результата в Redis на 1 час (ключ `need_id`), сброс при изменении потребности или профилей кандидатов из списка.

### 6.2. Итоговый скор

```
S = E · C^α · 1 / (1 + β · open_invites)        α = 1, β = 0,15
```

### 6.3. E-скор (подходит ли кандидат работодателю)

Все признаки нормированы в [0, 1].

| Признак | Как считается |
|---|---|
| `must_cov` | Среднее покрытие обязательных навыков. Навык из теста: `балл / 100`. Из резюме или проекта: 0,4. ФСП по профильной дисциплине: 0,8. Нет: 0 |
| `grade_fit` | 1 — грейд совпал, 0,5 — соседний |
| `ef` | Experience fit (6.5) |
| `skill_avg` | Средний балл подтверждённых тестом навыков / 100 |
| `fsp` | 1 — достижение в профильной дисциплине, 0,5 — в другой, 0 — нет |
| `fresh` | `exp(−дней_с_последней_активности / 60)` |
| `nice_cov` | Среднее покрытие желательных навыков |

**Гейт:** если покрытие хотя бы одного обязательного навыка < 0,3, кандидат не попадает в основной список, а уходит в «скрыты фильтром» (раскрываются кликом).

**Веса по грейду потребности:**

| Признак | Intern/Junior | Middle | Senior/Lead |
|---|---|---|---|
| `must_cov` | 0,25 | 0,30 | 0,20 |
| `grade_fit` | 0,20 | 0,20 | 0,15 |
| `ef` | 0,10 | 0,25 | 0,40 |
| `skill_avg` | 0,20 | 0,15 | 0,10 |
| `fsp` | 0,15 | 0,05 | 0,03 |
| `fresh` | 0,10 | 0,05 | 0,05 |
| `nice_cov` | — | — | 0,07 |

### 6.4. C-скор (подходит ли предложение кандидату)

| Признак | Вес (Senior/Lead) | Как считается |
|---|---|---|
| `salary_fit` | 0,35 (0,40) | 0 при `salary_to ≤ 0,9·min`, линейно до 1 при `salary_to ≥ 1,15·min` |
| `format_fit` | 0,20 | 1 — совпал, 0,5 — гибрид при желаемой удалёнке, 0 — иначе |
| `stack_interest` | 0,20 | Jaccard навыков потребности и «интересных» кандидату; −0,5 за каждую «нежелательную» |
| `domain_fit` | 0,10 | 1 — в «интересно», 0,5 — нейтрально |
| `benefits` | 0,10 | Доля отмеченных: ДМС, аккредитация, гибкий старт |
| `process` | 0,05 | 1 — до 2 этапов, 0,5 — 3, 0 — больше |

Для Senior/Lead `salary_fit` = 0,40, остальные веса уменьшаются пропорционально.

### 6.5. Experience fit

1. **Единицы опыта** кандидата (из проектов, опыта в резюме, достижений ФСП) и **требования** потребности извлекаются LLM по JSON-схеме (§9) и получают эмбеддинги e5 по полю `task + domain + skills`.
2. Для каждого требования `r` берутся 3 ближайшие единицы `e` кандидата.
3. Оценка пары:

```
sim  = clip((cos(r, e) − 0,75) / 0,15, 0, 1)        # пороги калибруются на 50 размеченных парах в день 5
s    = sim · trust · recency · depth
trust:   test/employer_task 1,0 · fsp_id 1,0 · github 0,8 · resume 0,6 · self 0,35
recency: 0,5 ^ (лет_с_даты / 2)
depth:   owner 1,0 · contributor 0,8 · participant 0,6
```

4. Покрытие требования (noisy-OR) и агрегат:

```
coverage(r) = 1 − Π (1 − s)  по трём лучшим e
EF = (Π_must coverage)^(1/n_must) · (0,7 + 0,3 · mean_nice coverage)
```

5. Для объяснения сохраняется лучшая пара по каждому требованию.

**КП:** на эталонном наборе из 10 потребностей × 30 кандидатов, размеченном командой, NDCG@10 нашей формулы выше, чем у сортировки по совпадению навыков (бейзлайн). Цифры обеих метрик показываются заказчику как доказательство качества.

## 7. Подсказки в MVP

### 7.1. Кандидату

Пересчёт по событию изменения профиля и ночью по всем кандидатам.

1. По всем активным потребностям специализации кандидата найти те, где он **отсечён ровно одним условием**: обязательный навык (нет или ниже 0,3), зарплата, формат, грейд.
2. Сгруппировать по причине, посчитать число и долю потребностей.
3. Добавить «ранговые» действия: пересчитать скор кандидата по выборке потребностей с изменённым признаком (`fresh = 1` для «решите задание», `trust = 1` для «подтвердите навык», `fsp` для «свяжите ФСП ID») и получить новое место в категории.
4. `priority = эффект / усилие` (усилие: мини-тест 10 мин = 1, проект = 2, изменение условий = 1); показать топ-3.

| Шаблон | Пример |
|---|---|
| Навык-блокер | «Подтвердите Kubernetes — +9 компаний (30 %). Мини-тест 10 мин» |
| Ранг | «Добавьте проект с Kafka: 12 → 7 место в категории» |
| Зарплата | «11 компаний отсекают вас по зарплате: ваш минимум выше 85 % вилок» |
| Формат | «Рассмотрите гибрид — +6 компаний» |

### 7.2. Работодателю

Считается по кэшированной подборке (до 300 кандидатов с признаками) — без новых запросов к БД.

| Тип | Расчёт | Пример |
|---|---|---|
| Сузить | Для кандидатных признаков (навык подтверждён тестом, опыт в домене, активен 14 дней, есть ФСП) — сколько останется и средний скор | «Kafka только подтверждённая: 24 → 9, соответствие 89 % → 95 %» |
| Расширить | Повторить фильтр без одного обязательного навыка (одна фоновая задача при сохранении потребности) | «Уберите обязательный Kubernetes: +40 кандидатов» |
| Вилка | Сколько кандидатов отсечено по зарплате, медиана минимумов в категории | «Вилка ниже медианы ожиданий: до 300 000 ₽ — +15 кандидатов» |
| Текст | LLM-чек-лист при сохранении: есть ли задачи, масштаб, стек, первые 3 месяца | «Опишите масштаб задач — точность подборки вырастет» |

Отбор: сужения ранжируются по росту среднего скора при пуле ≥ 5, расширения — по приросту пула. Показываются топ-3 разных типов.

## 16. Риски

| Риск | Вероятность | Мера |
|---|---|---|
| LLM медленная или недоступна на показе | Средняя | Все тексты сида сгенерированы заранее; разбор резюме демо-кандидата прогрет и закэширован; режим без LLM (§12) |
| Плохое качество подборок | Средняя | Эталон и калибровка в день 5; демо-потребности проверены вручную в день 7 |
| Piston требует привилегированный контейнер | Высокая | Отдельный хост или запуск только на демо-стенде; сеть контейнера отключена; лимиты |
| Keycloak и OIDC отнимут больше дня | Средняя | Готовый realm-export с клиентами и демо-пользователями в репозитории с дня 1 |
| Эмбеддинги на CPU тормозят на сиде | Низкая | Векторы считаются один раз при сиде и сохраняются в дампе |
| Расползание скоупа | Высокая | Этот документ; всё новое — в бэклог с пометкой «после показа» |
